# Faceface｜国际网站技术方案（尚未实测/未最终锁定）

## 从微信小程序迁移到国际网站

旧微信开发方式不再适用：微信相机接口、微信运行容器、微信小程序广告、微信包体与平台审核，全部从默认架构移出。新平台采用标准浏览器、HTTPS、移动优先响应式网页，支持 Android Chrome、iOS Safari 与常见桌面浏览器。

## 推荐架构

**建议（待实际验证，不是已建成）：** TypeScript + React + Vite 静态网站；把核心人脸处理、标准描述生成、古籍规则匹配和双报告拼装都放在浏览器端。优先部署静态资源与模型文件，不为当前不需要的账号、数据库、上传 API 搭建后端。若发现兼容性或规模需求，再评估框架调整。

数据流程：

1. 浏览器安全上下文（HTTPS）与用户主动视频授权。
2. MediaDevices.getUserMedia 前置实时摄像头，audio = false。
3. 本地拍摄质量/姿态/单人检测，合格时截取内存中的静帧。
4. 本地人脸关键点或轻量视觉模型（WebAssembly/WebGL/WebGPU 支持情况需真机验证）。
5. 标准词汇描述层：47项候选字段中优先选取跨区域高价值项，生成“脸型偏长、眼型偏细长、鼻翼较宽”等中性形态描述，无法看清标为 unknown。
6. 古籍匹配层：将现代描述ID映射到《麻衣相法》有出处的必要条件，计算完整符合、部分相似或条件不足；接入《易传·说卦》有文献支持的取象。
7. 报告层：同一判断记录输出简洁版/详细版；用户可以主动保存。
8. 页面结束：停止摄像头 tracks，释放无需保留的内存；不设业务图片上传端点。

## 已有研究不能等同于网站能力

- 旧 v1.6 Python/JS 原型测试通过，**但未完成MediaPipe真实478关键点运行**；没有国际网站程序。
- V2.5 有47项候选标准词；不是47项已识别能力。
- V2.6 技术分层为27关键点候选、11局部图像、3分割、5耳、1表情；这些数量是分配规划。
- V2.7/V2.8古籍映射大多属于“部分近似”与纸面检查；不能据此进行科学人格推断。
- 新网站可优先验证约12项跨区域形态，但最终范围必须由“视觉可行性 × 古籍匹配价值 × 手机性能”共同决定。

## 技术硬约束

- 浏览器摄像头权限必须在用户主动交互后申请；没有HTTPS安全上下文不能按正式Web部署方案使用。参考：https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia
- MediaPipe Web 可作为研究候选，但必须验证权重分发许可、Safari/Android手机支持、加载体积、运行延迟与内存。参考：https://ai.google.dev/edge/mediapipe/solutions/vision/face_landmarker/web_js
- “478关键点”不是478种面相分类，且不保证完整耳廓、发际、骨厚、神采等信息。
- 禁止将照片上传云端视觉大模型作为默认方案；网站CDN加载模型文件不能携带人脸图片或坐标。
- 镜像预览不等于真实解剖左右，耳相识别必须明确原始帧方向。
- 与拍照有关的页面不加载跟踪型广告SDK；即使之后引入广告也不得传输面部特征。
- 对支持的浏览器、设备、拒绝摄像头权限和低性能机提供诚实的降级/退出提示。

## 真机验收门

真实 Android Chrome + iOS Safari 上完成授权、预览、拍摄、停止、退回、补拍/跳过、分析与保存；使用实际本地模型而非假坐标；输出跨部位面部语义和未知标记；网络/本地存储可核验证明无面部数据泄漏。具体性能阈值在首轮真机基线后确定，不能先凭空承诺FPS。
